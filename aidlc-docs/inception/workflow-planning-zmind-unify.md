# Zmind 提交入口统一 - 执行计划

## 详细分析摘要

### 变更范围
- **变更类型**: 功能增强（对齐两个入口 + 新增 Redmine 附件上传）
- **主要变更**: 前端组件提取复用 + 后端新增 uploads 代理
- **涉及组件**: 前端 2 个页面组件 + 1 个 API 服务 + 后端 2 个路由文件

### 变更影响评估
- **用户界面变更**: 是 — 问题追踪表单新增项目树和附件上传
- **结构变更**: 是 — 提取共享组件
- **数据模型变更**: 否 — 无数据库 schema 变更
- **API 变更**: 是 — 新增 `/api/zmind/uploads` 路由
- **NFR 影响**: 否 — 无性能/安全架构变更

### 风险评估
- **风险等级**: 低
- **回滚复杂度**: 简单（独立功能，不影响现有数据）
- **测试复杂度**: 中等（需要 zmind API 可用性验证）

## 阶段决策

### 🔵 INCEPTION 阶段
- [x] 工作区检测 — **已完成**（棕地项目，已有代码）
- [x] 需求分析 — **已完成**（5 个功能需求已确认）
- [x] 工作流规划 — **进行中**
- [-] 用户故事 — **跳过**（内部功能对齐，无新用户角色）
- [-] 应用设计 — **跳过**（不新增组件架构，只提取复用）
- [-] 单元分解 — **跳过**（单一工作单元，无需分解）

### 🟢 CONSTRUCTION 阶段
- [ ] 功能设计 — **执行**
  - **理由**: 需要设计 Redmine uploads API 集成方案、共享组件接口、数据流
- [-] NFR 需求 — **跳过**
  - **理由**: 无新的性能/安全需求，复用现有机制
- [-] NFR 设计 — **跳过**
  - **理由**: 无 NFR 需求则无需设计
- [-] 基础设施设计 — **跳过**
  - **理由**: 无部署架构变更
- [ ] 代码生成 — **执行**（含规划和生成两部分）
  - **理由**: 核心实现工作
- [ ] 构建和测试 — **执行**
  - **理由**: 验证功能正确性
